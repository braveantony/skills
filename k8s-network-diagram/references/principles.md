# 共通原則

兩種風格（平面圖、3D 互動頁）都要遵守。這些都是使用者明確提出或否決過的事，每一條附上原因；遇到沒寫到的情況，照原因判斷。各風格的實際數值（色碼、字級、座標）在 `styles/<風格>/` 裡。

## 內容

1. **圖上的值只能來自 spec。** 範例檔的 IP、Pod 名稱、網卡名稱都只是示意。查不到的欄位留空，並在回覆中列出。原因：看起來完整、但數值是編的網路圖，會在排錯時誤導人。
2. **只執行唯讀指令。** tcpdump、ss、`cilium-dbg ... list` 這類觀察指令可以用；不建立測試資料、不改設定。
3. **圖上只放對應實際環境的資訊**：名稱、網卡、IP、網段、namespace、hostNetwork 標記。不放說明文字或比喻，說明寫在步驟裡。
4. **會變動的值用灰底**，例如 PID、Pod 名稱的雜湊後綴、Pod IP、lxc 名稱、來源埠。**步驟說明文字不加灰底。** 圖旁要有兩行註解（「灰底」兩字本身套灰底，當作圖例）：
   - 第一行依「圖上實際加了灰底的值」選：
     - 只有重啟或重建才會變的值（Pod 名稱、Pod IP、lxc 名稱）：「灰底的值會變動：重啟或重建後會不同」；
     - 圖上也有 PID 或來源埠：「灰底的值會變動：重啟、重建或每條新連線都不同」。
   - 第二行：「圖中是 <日期> <叢集> 實測，請以自己查到的為準」。
   - 兩種風格用同一份 spec 時，註解也要相同。
5. **同一份 spec，不同風格的步驟文字要逐字相同。** 使用者會在平面圖和 3D 頁之間切換對照。

## 視覺

6. **只用淺色主題**，不做深色模式。發布成 Artifact 時也一樣：Artifact 的頁面規範預設要支援深色，這裡例外，只寫淺色的 token，`body` 明確設定淺色背景，不加 `prefers-color-scheme: dark` 和 `[data-theme="dark"]` 區塊。原因：使用者明確否決過深色主題，兩種風格的配色也要能互相對照。
7. **兩個強調色只代表「哪一條連線」**：連線 ① 紫、連線 ② 綠，不用顏色表示方向。經過 proxy（Envoy、Gateway）時，用戶端到 proxy 是一條連線，proxy 到後端是另一條。其他元素一律用中性色。
8. **文字不能擋到圖案。** 標籤、步驟編號、膠囊、圖例都不能蓋到連線、網卡、交換器、主機、Pod、container，也不能互蓋或被邊緣切掉。原因：使用者看圖是為了看線怎麼走、經過哪張網卡；字一壓上去，圖就失去作用。放不下就換位置、拆圖或隱藏，絕不硬放。
9. **每個元件都要看得清楚。** 不能有接近背景色的元件（例如在白底上幾乎是白色的 container）。
10. **不畫商標**，瀏覽器、主機用無品牌的圖示。如果要用 Kubernetes 官方圖示，必須註明出處（kubernetes/community，CC BY 4.0；Kubernetes logo 是 Linux Foundation 的商標）。

## 用詞

11. 全部用繁體中文（台灣用語），用「連線」不用「連接」。元件名稱、IP、網卡名稱照 spec 原樣。
12. **圖上和步驟裡不要寫「ingress IP」**：讀者會以為是 K8s Ingress 物件的 IP。（查資料時的 Cilium 術語 `reserved:ingress` 不受限，只是不要直接搬到圖上。）Cilium Envoy 依 HTTPRoute 挑後端，步驟寫成「Envoy 依 HTTPRoute 挑一個 Pod，另開連線 ②」，第二行直接寫來源與目的位址。

## 工作方式

13. **交付前一定要看過成品**：轉成 PNG，或截圖後實際打開來看。給使用者看圖時：有 SendUserFile 就用它傳 PNG（`display: render`）；沒有時寫出完整路徑，或在回覆中附上圖。
14. **審閱**：使用者要求「請 Codex 和 Gemini 審」時，兩邊同時跑，只審閱、不改檔；每一項先自己核對，違反這份原則的建議放進「不建議改」，最後只問一個問題。指令、提示內容、整理方式與踩過的坑，都在 `styles/3d/verify.md`「請 Codex 和 Gemini 審閱」。
15. **沒處理的項目要說明原因，並提出可行的做法。** 能改的就直接改，不要因為麻煩而延後；真的是取捨時，說清楚兩邊的代價，讓使用者選。
16. **回報驗證結果時，說清楚涵蓋到哪裡為止**：量測或檢查了哪些狀態、沒涵蓋什麼。不要把「量測是 0」說成「沒有任何問題」。
